# KIT-ADR-0030: The door is a tool, not a place — intake from anywhere, and what is allowed to generate kit work

**Status**: Proposed
**Date**: 2026-08-09
**Deciders**: Fredrik Matheson (operator), Claude Code
**Extends**: KIT-ADR-0028 (versioned packages) — this applies that
decision to the one component it exempted: the setup door itself
**Related**: KIT-ADR-0027 (lean kit — shapes, degraded modes, the
doctor lifecycle rule), KIT-ADR-0024 (split-pair topology),
KIT-0066 (the intake flow), KIT-0081 (the live intake that surfaced
its gaps), `docs/STARTING-A-PROJECT.md`

**Retires**: the factory-clone precondition — the rule that project
creation happens *inside* an agentive-starter-kit checkout
(`docs/STARTING-A-PROJECT.md` "The factory model"; `project-intake`
"Where you run"; `bootstrap --help` "Kit-side only"). Nothing new is
built to replace it; the existing package and plugin channels absorb it.

**Existing mechanism this uses instead of inventing one**: the
`agentive-kit` PyPI package (already ships `doctor`, `preflight`,
lifecycle, `worktree`) and the `agentive-workflow` Claude Code plugin
(already ships every other agent). No new distribution channel.

## Context

The kit's stated purpose is to turn prototypes — typically Cowork
one-off deliverables — into repos that can be worked on systematically.
The operator's report, 2026-08-09:

> "At the moment, I am spending more time working on getting ASK back
> on track than I am on taking Cowork one-offs and turning them into
> usable software."

Four requirements were named: (1) Cowork session → systematic repo;
(2) low friction to *start* that conversion; (3) easy to keep projects
current as the kit develops; (4) does not require working on the kit
just to get a project going.

Requirement 3 is largely solved. KIT-ADR-0028 made agents ship via the
plugin and scripts via PyPI; projects carry pins, so the kit moving
forward cannot break a project nobody is looking at, and updating is
`uv tool upgrade agentive-kit && claude plugin update` with `agentive
doctor` reporting whether it mattered.

Requirements 2 and 4 fail, and they fail at one line.

### The factory-clone precondition

ADR-0028 packaged everything a project *contains*. It did not package
the thing that *creates* a project. The door remains kit-side by
explicit declaration:

- `scripts/local/bootstrap --help`: "Kit-side only: runs from an
  agentive-starter-kit clone against a target; never ships on any sync
  tier or consumer rsync."
- `.claude/agents/project-intake.md`: "**Where you run**: from an
  agentive-starter-kit checkout — the door is kit-side only and does
  not ship to consumer projects."
- `docs/STARTING-A-PROJECT.md`: "You start a session in
  `agentive-starter-kit/` … to create projects."

So every graduation begins `cd ~/Github/agentive-starter-kit && claude`
— a session opened inside the repo the operator is trying to stop
working on, with its backlog present and a planner whose job is to
triage it. The intake path runs *through* the kit's own workspace. That
is the structural cause of "I spend more time on the kit than on the
work," and no amount of process discipline removes it, because the
precondition is architectural.

The exemption was never argued. It is a residue of the pre-package era,
when the door had to be kit-side because the door's job was to *copy
the kit tree*. After KIT-0093, `--new` projects are born packaged —
a content scaffold plus pins, no script copies — so the door's output
is package data, not an rsync of a working tree. The reason for the
exemption expired; the exemption did not.

### The second generator: audits

A separate cause, same symptom. Kit work is currently generated by
**auditing the kit**. The 2026-07-24 pre-0.9.0 sweep produced 92
confirmed findings (40 stale-doc, 29 contradiction, 15 version-drift,
6 orphan) and spawned KIT-0065/0067/0068/0069 — roughly a quarter of
work, generated by inspecting the kit rather than by using it.

Compare KIT-0081: one live intake (`ev-fast-charging-loads`,
2026-08-04) produced nine concrete gaps, none blocking, all small, every
one traceable to a moment that cost the operator something. An audit
surfaces every statement that has gone false. A live run surfaces the
ones that are load-bearing. Those are different sets, and only the
second is bounded by demand.

The kit is its own only consumer, so "wrong" has had no victim outside
the kit — which is how audit-driven work came to be the default
generator.

## Decision

### D1 — The door ships in the package

`agentive new` and `agentive adopt` become console subcommands of
`agentive-kit`, taking the same flags, matrix, preset resolution, and
records as `scripts/local/bootstrap` today. The door stops being a
place you must stand and becomes a tool you have installed.

- `new` ships first: post-KIT-0093 its scaffold is enumerated content,
  packageable as package data.
- `adopt` follows when ADR-0028 phase 3 lands and it stops copying
  script trees.
- `scripts/local/bootstrap` becomes a thin `exec` shim into the
  package for one release, then goes — per KIT-ADR-0027 P3's rule that
  convergence is structural, not social, and that the removal task is
  filed with the PR that creates the shim.
- The shape × profile matrix keeps its single owner; ownership moves
  with the code, it is not duplicated.

**Consequence**: `cd ~/Github && agentive new my-thing` works from
anywhere. The kit clone reverts to being the *development* home for the
kit, entered when working on the kit and at no other time.

### D2 — `project-intake` ships in the plugin

With D1 landed, the "must run from a kit checkout" constraint on the
intake agent has no basis. `project-intake` moves into
`agentive-workflow` alongside every other agent.

The intended flow becomes: **open Claude in the Cowork output folder
and run the intake there**. The deliverable is the input, in place. No
navigation, no clone, no factory.

### D3 — The handoff brief stays primary; derivation is a declared degraded mode

*(Operator decision, 2026-08-09, correcting an earlier proposal to make
the brief optional-by-derivation.)*

The `PROTOTYPE-HANDOFF-TEMPLATE` brief is **the preferred input and
stays so**. Its value is not a file inventory — it is the *rationale*:
why the prototype was built the way it was, what is solid versus rough,
which decisions were deliberate. **Inspection can recover what was
built; it can never recover why.** Until a Cowork session's agent and
the resulting code session's agent can talk to each other directly, the
brief is the only carrier for that knowledge, and asking for it at the
end of a prototyping conversation remains the right practice.

Therefore, when no brief exists, intake does not block and does not
invent:

- It derives a brief **from inspection only** — files, dependency
  manifests, entry points, READMEs, git history if any.
- Every section the template defines that inspection cannot support —
  decisions and their reasons, solid-versus-rough, known issues,
  intended next steps — is emitted verbatim as
  `> RATIONALE NOT RECOVERABLE BY INSPECTION — no handoff brief was
  supplied.` It is **never** filled with a plausible inference.
- The derived file is named and marked as derived, and the intake's
  output says so, so that a following agent reads it as a partial
  record rather than as fact.
- The operator is offered the template block to fill the gap, then or
  later.

This is KIT-ADR-0027 P5's principle applied to intake inputs: degraded,
loudly — never silently green. A fabricated rationale is worse than an
absent one, because the following agent cannot tell the difference.

### D4 — A graduation ladder, with rung 0 as a resting place

Three rungs, built from shapes that already exist. `--no-kit` is
currently `adopt, single only`; rung 0 makes it a first-class `--new`
outcome.

| Rung | What the project gets | Reached when |
|---|---|---|
| **0 — repo** | git + GitHub + README + CI running the profile hook + a place for tests. No `.kit/`. | every Cowork deliverable, immediately |
| **1 — tracked** | `.kit/` task folders, ADR home, planner-ready; single repo | it survived a week and you want to change it |
| **2 — split pair** | planning repo + clean code repo (KIT-ADR-0024) | others will read the code, or it goes to production |

**Rung 0 is a legitimate terminal state.** Most one-offs should stay
there, and that reads as success, not as an unfinished install. Nothing
in doctor, preflight, or any agent may report rung 0 as a deficiency.

Promotion is `agentive adopt` on the same folder later — which works
because the door records resolved choices in the CLAUDE.md kit-install
region and re-reads them (KIT-ADR-0027 P3).

### D5 — What is allowed to generate kit work

> Kit work is triggered by a defect that blocked or degraded a real
> project intake, or by a release obligation. Not by an audit.

Supporting mechanics:

- **One queue.** Project work and kit work share a backlog. Kit work
  currently has no competing entries, so it does not win — it runs
  unopposed.
- **A WIP cap**: at most two open kit tasks not traceable to a live
  project. This ADR follows its own rule — it files tasks for D1 and D2
  only; D3/D4/D6 are sequenced here and filed when D1 lands.
- **Automation replaces sweeps.** `doctor.d/`, `plugin-drift.yml`, and
  the retro-closure lifecycle rule (KIT-ADR-0027 P4b) are the standing
  substitute for periodic audits, not a complement to them. Every check
  added there is a sweep never run again.
- **The premise challenge stays.** The 2026-08-08 practice — testing
  the premise of open backlog items and archiving with evidence-bearing
  dispositions — is retained. It is demand-reduction, not generation.

An audit is not forbidden; it stops being the default. Running one is
itself a decision that should name what changed to justify it.

### D6 — The intake acceptance test is the definition of "the kit works"

Extend `tests/test_scaffold_acceptance.py` to run the full intake
end-to-end in CI against a fixture prototype folder: create → `agentive
doctor` → **assert every file path referenced by the seeded agents
exists in the created tree**.

That last assertion is KIT-0081 F2 — found by hand, by grepping the
seeded `planner.md` and `feature-developer.md` for `docs/…` and `.kit/…`
paths and testing existence; it caught a planning scaffold shipping
without `docs/CROSS-REPO-PATTERN.md`, the document its own seeded
planner routes every git operation by. A machine should do that on
every push.

When this test is green, the kit does not need visiting. That is the
mechanism that makes D5 safe to hold to.

## Consequences

**Positive**

- Requirements 2 and 4 are answered structurally rather than by
  discipline: the intake path no longer passes through the kit's
  workspace.
- Requirement 1 gets a shorter path — intake runs in the deliverable
  folder itself.
- Requirement 3 is unchanged and already working (pins + two upgrade
  commands + doctor).
- No new mechanism, no new channel, no new config surface. Two
  subcommands move into a package that already exists and an agent
  moves into a plugin that already ships thirteen others.
- The kit's own front door becomes the thing every consumer runs, so
  door defects surface in real use rather than in audits — closing the
  loop D5 depends on.

**Negative / risks**

- Door logic is shell (`bootstrap` + the three engines); moving it into
  a Python package is a port, not a copy. Mitigation: the engines can
  be invoked as packaged data scripts initially, with the argument
  parsing and matrix ownership in Python; a full rewrite is not
  required to get the addressability win.
- Two release surfaces move in step for one cycle (package + plugin).
  The 2.0.0 drift guard (KIT-0096) already covers the plugin half.
- Rung 0 risks becoming a place projects rot in. Accepted deliberately:
  a repo that rots at rung 0 cost one command; a split pair that rots
  cost two repos and a token.
- D5 will let some true-but-unimportant staleness persist. That is the
  intended trade. The cruft audit's own distribution — 40 of 92
  findings stale-doc — is the evidence that sweeping is unbounded.

**Explicitly not proposed**

- Changes to the ADR template. Discussed separately; not bundled here.
- Retiring the handoff brief (D3 settles this: it stays primary).
- Any change to the split-pair topology itself (KIT-ADR-0024 stands);
  D4 changes only *when* a project is put into it.
- A Cowork↔code-session agent channel. That is the real fix for D3's
  rationale gap and is out of the kit's reach today; recorded as a
  revisit trigger below.

## Recommended sequence

**D1 → D2 → D3+D4 → D6.** D5 is a policy adoptable immediately at zero
cost, and it is what buys the time for the rest.

D1 is load-bearing: until the door ships, every other move still starts
inside the factory.

## Revisit Triggers

- **A Cowork session agent and a code session agent can address each
  other directly.** D3's derived-brief fallback becomes largely
  unnecessary; the rationale transfers live rather than through a file.
- A second operator (rung 0's "resting place" convention needs to
  become explicit onboarding text).
- A non-Python profile becomes the majority case (the door's Python
  packaging becomes a question rather than an obvious fit).
- Kit tasks exceed the D5 WIP cap for two consecutive months — the cap
  is wrong, or the generator rule is being routed around.
